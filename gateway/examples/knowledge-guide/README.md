# Справочник Платформы для dev

Одноразовый запуск с компьютера, где есть браузер. Справочник находит однозначный адрес MCP и портал входа в паспорте стенда. По слову или фразе он возвращает выдержку из разрешённого документа, его название и путь. Если данных недостаточно, сообщает об этом. В первой версии ответы извлекаются из текста без обращения к внешней модели.

## Что нужно от администратора

Для разработки достаточно вымышленного пользователя. Для проверки живого входа нужен отдельный активный внутренний пользователь портала akmetron.bitrix24.ru с подразделением. Достаточно несекретного числового ID или ссылки на профиль. При регистрации на стенде ответственный сам входит в браузере под этой записью. Пароль, коды входа и токены остаются у него.

## Подготовка dev перед первым живым входом

- Отдельное dev-приложение Битрикс24 и публичный HTTPS описаны в [регламенте dev](../../../tools/platforma-workflow/README.md). Право приложения на стороне портала — `user_brief`.
- Gateway сопоставляет `GATEWAY_KNOWLEDGE_GUIDE_SUBJECT` с полной идентичностью `bitrix24:<member_id портала>:<числовой ID пользователя>`. Используйте member_id из закреплённой конфигурации dev и учётную запись, выделенную справочнику. Владелец Платформы для этой роли не подходит.
- Набор разрешённых MCP-методов — `gateway_access_profile`, `gateway_knowledge_search`, `gateway_knowledge_document_get`. Старый метод чтения собственного профиля требует `skills:read`, документы требуют `knowledge:read`. Сервер дополнительно ограничивает список методов даже для ранее выданного токена. Запись телеметрии о запуске в эту версию роли не включена. Для отзыва чтения оставьте роль назначенной и установите запрет `knowledge:read` именно этой учётной записи. Для полного отключения используйте штатный запрет пользователя. Простое снятие роли возвращает обычную модель сотрудника.
- На пустом dev подготовьте конфигурацию для просмотра перед установкой. В dev-data/profiles.example.json перечислены разрешённые пути общих знаний. Для нового тестового комплекта ключ шаблона `dev-guide-catalog-template` должен совпадать с `GATEWAY_PLATFORMA_OWNER_SUBJECT`; это ключ шаблона каталога, а не логин агента. `GATEWAY_ADDON_PROFILES_FILE` указывает на файл каталога. Если конфигурация уже есть, используйте её штатный шаблон и сохраните его содержимое. Установите единственный стартовый документ dev-data/project-profile.md в `spaces/organizational-awareness/awareness/project-profile.md` относительно корня тома общих знаний. Для поиска достаточно тех разрешённых файлов, которые уже опубликованы.
- Первичный вход выполняется через OAuth в браузере. Клиент открывает только адрес авторизации dev и принимает ответ на локальном порту. Реквизиты и токены хранятся в памяти процесса до его завершения. Это ручной пилот без расписания.

## Запуск после настройки стенда

Используйте Python 3.12 и отдельное окружение с версиями из [репозиторного lock-файла](../../locks/runtime.txt). Для клиента нужны `mcp==1.27.0` и `httpx==0.28.1`.

Из каталога справочника выполните:

```text
python guide.py --check
```

Команда проверяет доступность dev, HTTPS, готовность шлюза, объявленные адреса и права OAuth, страницу входа и требование авторизации на MCP. При ошибке она подсказывает следующий шаг. Проверку можно выполнить до создания учётной записи агента. Для неё нужны только установленные зависимости клиента.

Успешный результат содержит `connection_ready: true` и `account_checked: false`. Личность агента, его права и правильность реквизитов приложения проверяются при последующем входе. Запросы диагностики могут учитываться в обычном журнале HTTP шлюза. Сама проверка не открывает браузер, не регистрирует OAuth-клиента и не вызывает методы MCP.

После успешной проверки выполните вход и запрос:

```text
python guide.py --subject "bitrix24:<member_id портала>:<ID агента>"
python guide.py --subject "bitrix24:<member_id портала>:<ID агента>" --find "Справочник"
```

Запуск с `--subject` выполняет вход, проверяет ожидаемую личность, права и точный список доступных инструментов. Контрольный ответ для стартового документа должен назвать dev-адрес, портал входа и путь `awareness/project-profile.md`.

Проверка подключения также автоматически выполняется перед входом. При проблемах с DNS, HTTPS или настройкой dev она завершает запуск с пояснением. Тексты сетевых исключений и адреса с параметрами авторизации в сообщения диагностики не включаются.
