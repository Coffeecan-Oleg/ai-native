# UniSender: первая проверка только на вымышленных показателях

Выбранный владельцем этап: общая песочница и прежний личный вход через Яндекс.
Одна новая операция `platforma.unisender-demo.stats.get` вызывается через
`gateway_call_tool` с `arguments_json={"campaign_id":"LAB-UNISENDER-001"}`.
Маршрут использует существующее разрешение `platforma:read`, проверку ресурсов,
ограниченный профиль и аудит Gateway. Для старых OAuth-подключений потребуется
новый личный вход: их подписанный список маршрутов автоматически не расширяется.

Это локальная неизменяемая фикстура: нет импорта сетевого клиента, чтения ключей,
обращений к UniSender, списка реальных кампаний, адресатов, текста письма, отправки
или записи. Чужой ID, дополнительные параметры и другие методы отклоняются.
Каждый ответ помечен `synthetic=true`, `real_unisender_connected=false` и содержит
источник `platforma-training:unisender-demo#LAB-UNISENDER-001`.

Ожидаемые показатели: total=100, sent=100, delivered=98, read_unique=25,
read_all=30, clicked_unique=7, clicked_all=9, unsubscribed=1, spam=0.
Это девять полей официального getCampaignCommonStats. Отдельного счётчика ошибок
в этом методе нет; sent−delivered нельзя выдавать за число ошибок.
https://www.unisender.com/ru/support/api/statistics/get-campaign-common-stats/

Проверка коллегой:
1. Обновить личное MCP-подключение Платформы через Яндекс, если маршрут не разрешён.
2. Попросить найти учебную операцию по слову `unisender`.
3. Прочитать LAB-UNISENDER-001, показать девять показателей и источник, явно назвать
   данные вымышленными. Это демонстрация инструментов, а не применение навыка.
4. Попробовать LAB-UNISENDER-002. Ожидается отказ, без подбора других ID.
5. Владелец видит обращение в «Журнале событий» как gateway_call_tool и
   resource_access с именем маршрута. События запуска навыка не выдумываются.

Публичная поставка не включает исходный архив Sites, его project_id, секреты или
учётные данные Дарьи. Её код служит проверенным примером проекции показателей;
для текущего этапа реализована отдельная учебная фикстура за существующим шлюзом.
Реальный API потребует отдельного адаптера, новой ограниченной политики кампаний
и пользователей и защищённого ввода нового ключа после согласования владельца
данных. Публикация Sites для выбранной схемы не нужна.

При применении после согласования добавляется только этот read-route в конечный
список OAuth-маршрутов и приватный профиль владельца; сроки, scopes, существующие
grants и записи БД сохраняются. Динамический профиль одобренных коллег получает
тот же учебный read-route при прежнем действующем одобрении. Новых MCP-функций
верхнего уровня, миграций и прав на реальный сервис нет. Плагин 0.6.0 сохраняется.
