# Корпоративный вход через Битрикс24

Состояние: подготовлено на копии, не включено на работающем Gateway.
Целевой портал — только `akmetron.bitrix24.ru`.
Первое включение — на текущем `kromin.axion-test.akmetron.ru`; перенос домена отдельно выполняет коллега.

## Сценарий

Веб-панель и MCP OAuth перенаправляют сотрудника на собственный портал.
Сервер обменивает одноразовый код на токены. Для идентификации вызывает
`user.current`, затем `user.get` для того же ID. Требуются ACTIVE=true/Y,
USER_TYPE=employee, положительный UF_DEPARTMENT. Поля проверяются в ответе:
доверять только фильтру нельзя, так как Битрикс может игнорировать неизвестный фильтр.

Доверенный `member_id` берётся из ответа сервера OAuth; `client_endpoint` должен
строго равняться `https://akmetron.bitrix24.ru/rest/`. Домены из callback не выбирают
адрес API. После первого реального входа рекомендуется закрепить полученный
member_id в защищённой конфигурации. Пустой pin не разрешает другой портал:
локальное приложение и точный REST endpoint остаются обязательными.

Пользователь имеет новый стабильный subject `bitrix24:<member_id>:<user_id>`.
Прежние Yandex subjects, email-алиасы, группы и admin grants не наследуются.
Старая память, авторство загрузок и статистика сохраняются под прежними ID;
автоматического объединения аккаунтов по email нет. Для переноса владения
нужна отдельная явно проверенная связка идентичностей.

## Базовый доступ

Автоматически активным внутренним сотрудникам доступны общая карта из прежнего
разрешённого каталога документов, встроенные/загруженные навыки, учебные сервисы
и заявки (включая создание/изменение вымышленных записей), загрузка/переименование
своих новых навыков через личную веб-сессию, собственные события навыков и аудит.
Личная память, чужие журналы, управление, удаление и реальная CRM не входят в baseline.

Рабочий UniSender выдаётся отдельным явным списком Bitrix user IDs. Первоначально
предлагается только владелец 3318. Автоматическое предоставление рабочего UniSender
всем новым сотрудникам не выполняется. Отправка писем и изменение UniSender не добавлены.

Владелец задаётся точным ID учётной записи портала. В текущей браузерной сессии
наблюдался пользователь 3318; окончательная привязка проверяется личным OAuth-входом.
Нельзя назначать владельцем первого посетителя или автоматически наследовать admin Битрикса.

## Локальное приложение

- Тип: серверное локальное приложение на целевом портале.
- Название: `Платформа Акметрон — корпоративный вход`.
- Обработчик: `https://kromin.axion-test.akmetron.ru/auth/bitrix24/callback`.
- Первоначальная установка: `https://kromin.axion-test.akmetron.ru/auth/bitrix24/install`.
- `Приложение само завершает установку`: выключено, штатное завершение порталом.
- Единственный scope: `user_brief` — «Пользователи (минимальный)».
- Удалить стандартный CRM scope перед созданием. Не выбирать полный `user`, CRM,
  сообщения, диск или права записи.

Начальная установка и POST из фрейма показывают ссылку на отдельный личный вход.
Присланные в таком POST токены администратора не импортируются и не доказывают,
кто входит. Browser-bound OAuth с одноразовым state обязателен.

## Защищённая конфигурация

```text
GATEWAY_LOGIN_PROVIDER=bitrix24
GATEWAY_BITRIX_PORTAL=akmetron.bitrix24.ru
GATEWAY_BITRIX_CLIENT_ID=<hidden input>
GATEWAY_BITRIX_CLIENT_SECRET=<hidden input>
GATEWAY_BITRIX_OWNER_USER_ID=3318
GATEWAY_BITRIX_UNISENDER_USER_IDS=3318
GATEWAY_BITRIX_MEMBER_ID=<pin after verified login>
GATEWAY_BITRIX_DENIED_USER_IDS=
```

App secret — только закрытый серверный файл 0600, не Git и не клиент.
Access+refresh токены каждого пользователя сохраняются существующим Fernet-хранилищем
PostgreSQL в зашифрованном envelope. Refresh токен не хранится в открытых metadata.
Разрешён только read-only user_brief. OAuth-коды и query auth-эндпоинтов убираются
из Uvicorn access log. Ответы об ошибках не содержат реквизитов и сырых upstream-ошибок.

В живом ответе сервера авторизации поле `scope` может содержать служебное `app`.
Это не принимается за подтверждение прав REST. При первом входе и обновлении пары
токенов Gateway отдельно вызывает `/rest/scope.json` на закреплённом портале без
параметра `full` и требует ровно `user_brief`. Дополнительные права или отсутствие
этого подтверждения закрывают вход. Права приложения в Битрикс24 не расширяются.

Чтение собственного профиля MCP в корпоративном режиме требует `skills:read`.
Прежнее требование `access:request` сохранено только для старого режима.
Пакеты доступа ищутся по точному Bitrix subject, без совпадений по имени или email.
Отказы входа записываются в аудит только фиксированными кодами причин.

Статус сотрудника проверяется повторно с кэшем максимум 60 секунд на процесс;
существование/отзыв локальной записи проверяется каждый раз. При ошибке API или
отсутствии обязательных полей доступ закрывается. Обновление Bitrix-токенов
сериализовано advisory lock PostgreSQL. Cache miss выполняет ограниченные HTTP
проверки; нагрузочная приёмка и влияние на браузерные обработчики ещё не проверены.

Профиль старого владельца используется лишь как каталог уже общих документов и
описаний телеметрии. Срок 31 октября не продлевается в старых grants. Новые сессии
живут по условию действующей внутренней учётной записи. Это отдельный согласуемый
режим корпоративного доступа, а не отключение авторизации или выдача wildcard.

## Применение и откат

До применения: ревью diff, закрытая копия БД/томов/конфигурации, сохранённый digest
предыдущего образа. Сначала образ с обратной совместимостью при provider=yandex,
затем регистрация приложения, защищённый ввод реквизитов и переключение env.
Обновляется только Gateway, сохраняются PostgreSQL и тома. Новая миграция не нужна.

Минимальная живая проверка: `/join` → личный Bitrix-вход владельца → MCP OAuth →
профиль → каталог/один навык, затем вход обычного сотрудника при возможности.
Внешние/уволенные, поддельный portal, callback replay и чужие данные проверены
синтетическими тестами; это не заменяет приёмку реальных аккаунтов на портале.

Откат: вернуть предыдущий digest и env из закрытой копии. Не накатывать старую
полную БД поверх новых событий. Записи Bitrix остаются зашифрованными и не принимаются
при provider=yandex. Старые Yandex-сессии в корпоративном режиме не принимаются.

Перенос домена позднее требует согласованно обновить callback приложения,
PUBLIC_URL/ISSUER_URL/RESOURCE_URL и личные подключения сотрудников.
