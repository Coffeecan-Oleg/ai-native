# Платформа внутри Битрикс24

## Что увидит сотрудник

Сотрудник открывает установленную Платформу из меню Битрикс24. Система проверяет
его учётную запись и открывает панель в том же окне. Внутренние разделы панели
остаются в этом окне. Повторно вводить email, ключи или переходить на Яндекс не нужно.

Права прежние: активному внутреннему сотруднику доступен согласованный базовый
профиль; администрирование остаётся у владельца; UniSender отключён до отдельной задачи. Личные данные
старых аккаунтов не объединяются. Подключение ИИ-приложения по MCP по-прежнему
проходит отдельный личный OAuth: открытие веб-панели не подключает чужой ассистент.

## Первый запуск после включения

Владелец ID 3318 первым открывает существующее приложение в Битрикс24. После проверки
его реального пользовательского токена, минимальных REST-прав и кода приложения
сервер однократно сохраняет защищённый хеш APPLICATION_TOKEN. До этого сотруднику
показывается сообщение о необходимости первого запуска владельцем.

Источник не заменяется повторным запросом установки или запуска. APP_SID не служит
ни идентичностью сотрудника, ни эталоном APPLICATION_TOKEN. Смена секрета приложения
потребует отдельной процедуры повторного закрепления источника.

## Реализация

- Переключатель: GATEWAY_BITRIX_EMBED_ENABLED=true; по умолчанию режим выключен.
- Используется текущий обработчик POST /auth/bitrix24/callback; настройки приложения
  и разрешение user_brief не меняются. GET callback обычного OAuth сохраняется.
- Страница установки не превращается в пользовательский вход. Нет fallback на
  токены установившего приложение администратора.
- Проверяются Origin портала, DOMAIN, APP_SID, закреплённый member_id,
  APPLICATION_TOKEN, фактический scope, app.info.CODE/STATUS/INSTALLED, user.current
  и user.get. URL серверных запросов заданы кодом, входящие SERVER_ENDPOINT и USER_ID
  не используются для выбора сервера или идентичности.
- Для первого закрепления источника требуются доказанные токеном user.current
  ID 3318 и совпадение app.info.CODE с текущим Client ID. Конкурирующие запросы
  сериализуются advisory lock PostgreSQL. Сохраняется только хеш источника,
  дополнительно зашифрованный существующим хранилищем; отдельная БД не нужна.
- Личные access/refresh токены сохраняются отдельно для точного Bitrix subject
  в существующем зашифрованном хранилище. Реквизиты не выводятся в HTML или журнал.
- Cookie встроенного сеанса отдельная: __Host-gateway_bitrix_frame, Secure,
  HttpOnly, Path=/, SameSite=None, Partitioned, срок 8 часов. Сессия обычной
  внешней панели сохраняет прежнее поведение.
- Подпись JWT привязывает новый токен к каналу bitrix24-frame. Этот токен
  не принимается MCP-транспортом и не подменяет обычную browser-cookie.
- Встраивание панелей разрешается только для https://akmetron.bitrix24.ru.
  Остальные директивы всех CSP сохраняются. Внешние страницы и MCP не получают
  общего разрешения на встраивание.
- Для изменений из встроенной сессии проверяется точный Origin Gateway;
  существующие CSRF-токены и проверки форм остаются обязательными. Native launch
  от родительского Битрикс24 проходит отдельную строгую проверку Origin портала.
- Выход очищает разделённую cookie. Если сессия завершилась или cookies блокирует
  браузер, показывается сообщение в текущем окне вместо внешнего перехода.

HTTP-адаптер проверен для фактически установленного MCP SDK v1. С включённым
встроенным режимом переход на SDK v2 останавливается до отдельной проверки адаптера.

## Проверка и изменения конфигурации

Для будущего изменения после согласования: закрытая копия конфигурации, БД и томов;
проверенный образ; обновление только Gateway. Первичное включение флага уже выполнено;
повторять его при обычном использовании не требуется.
PostgreSQL, роли, scopes, MCP-подключения и UniSender не меняются.

Приёмка: владелец запускает приложение в Битрикс24; появляются панель и каталог
навыков внутри того же окна; учебные заявки в корпоративном режиме закрыты. Затем проверяются сотрудник,
переходы между разделами, выход и повторное открытие; native MCP остаётся доступным.
Нужна проверка целевых браузеров: строгие корпоративные политики хранения данных
могут блокировать даже разделённые cookies. Приёмка владельцем зафиксирована отдельно; результат обычного сотрудника ещё ожидается.

Откат: вернуть предыдущие образ и env из закрытой копии либо отключить флаг.
БД не восстанавливается поверх новых записей. Не удаляются личные токены и данные.
