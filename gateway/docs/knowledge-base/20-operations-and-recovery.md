# Проверка состояния и восстановление Платформы

Для администратора. Проверено 8 ноября 2026 года. Рабочий адрес — https://platforma.akmetron.ru. Техническая проверка сервера не заменяет вход и выполнение задания обычным сотрудником.

## Что можно проверить одной командой

В комплекте инструментов `tools/platforma-workflow` подготовлен `operations_check.py`. Запускайте его на компьютере администратора с Python 3 и OpenSSH. Нужен существующий SSH-конфиг с именем `platforma-production`, проверенным ключом сервера и личным доступом. Скрипт не выдаёт новых прав.

Из корня репозитория:

```text
python tools/platforma-workflow/operations_check.py --ssh-config SSH_CONFIG --expected-revision f95be3a63c65417ef821f278dba7095d7098cf68 --output operations-report.json
```

Замените `SSH_CONFIG` путём к своему конфигу. Полный номер версии берите из отчёта принятого выпуска; после следующего выпуска он изменится. Версия схемы 28 и ожидаемый формат тега закреплены в этой редакции проверки. При изменении контракта их нужно обновить с тестами.

Скрипт вызывает только `status`, `version`, `counts` и четыре публичных HTTP-адреса. Проверяет Gateway и PostgreSQL, версию кода, схему, включённую авторизацию, отказ анонимному MCP, закрытые метрики и текущий адрес OAuth. Не выполняет перезапуск, импорт, миграции и бизнес-операции. Не читает конфигурацию с секретами и не сохраняет полный вывод сервера.

Результат — JSON-файл и код завершения. `0` означает, что все технические проверки прошли. `1` означает ошибку или отсутствие подтверждения. `unknown` — ответ не удалось получить, а не доказательство поломки. В отчёте отдельно перечислены непроверенные условия: вход сотрудника, внешние копии, восстановление production, квота, уведомления и контроллер выпуска.

8 ноября живой запуск подтвердил все 12 технических проверок версии `f95be3a`. Это одноразовая диагностика: постоянного расписания и отправки сообщений она не включает.

## Если что-то не работает

1. Попросите сотрудника указать время, приложение, шаг и текст ошибки. Не просите токен, пароль или полный адрес обратного входа с параметрами.
2. Выполните диагностику. Если недоступен только один клиент, сначала проверьте его подключение и личный вход. Работающая веб-панель не доказывает доступ MCP из чата.
3. Если сервер или база не отвечают, сохраните нормализованный отчёт. Полный журнал просматривайте в закрытой административной среде. Не публикуйте секреты и запросы сотрудников.
4. Не исправляйте отказ доступа выдачей всем прав администратора. Сверьте конкретного пользователя, инструмент и роль.
5. Если после выпуска проблема затронула всех, остановите дальнейшие изменения и выберите проверенный способ исправления. После появления новых записей нельзя автоматически возвращать старую базу.

Для первичного обращения достаточно: время, приложение, шаг, код ошибки, идентификатор серверного запроса, если он получен, и скриншот без секретов. Недоступный инструмент в чате и серверный отказ — разные результаты.

## Что проверено при восстановлении

На отдельной временной копии поднят тот же принятый образ `platforma-gateway:evening-f95be3a63c65`. Использованы только специально созданные вымышленные данные и новые временные ключи. Production-база и секреты не копировались.

Проверены полный цикл дампа и восстановления PostgreSQL, 49 таблиц схемы 28, точное содержимое опубликованного навыка и три контрольных файла в хранилищах knowledge, requests и audit. После восстановления Gateway стал healthy с включённой авторизацией; анонимный MCP вернул 401. Репетиция заняла 92,18 секунды.

Контейнеры работали без опубликованных портов, во внутренней сети, с общим пределом памяти 352 МиБ. Временные ресурсы удалены. Ранее работавшие контейнеры не перезапускались. Скрипт репетиции — `tools/platforma-workflow/tests/rehearse_restore_current.py`; он предназначен для разрешённого dev-хоста, не для production.

Это проверка процедуры на маленькой вымышленной базе. Она не определяет время восстановления реальных объёмов и не подтверждает существование внешней резервной копии, перенос на другую машину или полноценный корпоративный вход после аварии.

## Что ещё нужно для защиты от потери сервера

Нужно выделить закрытое хранилище вне машины Платформы, определить ответственного и срок хранения, согласовать допустимую потерю данных и срок возврата в работу. В план копирования входят база, прикладные файлы, конфигурация и материалы для восстановления секретов — с отдельным контролем доступа.

После настройки нужно реально восстановиться из внешней копии в изолированную среду и проверить вход, чтение навыка, права и журнал. Только тогда можно закрывать этот пункт. Копия на том же сервере и артефакты GitHub Actions его не заменяют.

## Выпуск и откат

Перед миграцией закрывают вход и останавливают записи, затем снимают финальный проверенный снимок, применяют миграцию и проверяют кандидата. До открытия можно вернуть согласованный снимок без потери новых пользовательских записей, поскольку их ещё не было. После открытия нужен совместимый выпуск вперёд либо отдельно согласованный возврат с учётом новых данных.

В production новый контроллер окна ещё не подключён. Его наличие в исходниках и работа в dev не меняют ограниченный SSH-интерфейс рабочего сервера. Эта работа остаётся за инфраструктурным доступом.

Проверка обычным сотрудником, внешнее хранилище, production-контроллер и приёмка доставки аварийных уведомлений остаются открытыми. UniSender остаётся отключённым по решению владельца.
