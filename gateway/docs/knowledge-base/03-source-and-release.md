# Корпоративный Gateway: исходники и проверяемая сборка

Этот раздел предназначен для разработчика и администратора. Сотруднику для работы
с навыками не нужно собирать Docker-образ или получать доступ к секретам сервера.

## Что находится в репозитории

Ветка корпоративной Платформы находится в форке
[Coffeecan-Oleg/ai-native](https://github.com/Coffeecan-Oleg/ai-native).
Корпоративный код расположен в каталоге `gateway`. Исходники приложения,
маршруты, миграции, библиотека встроенных навыков, тесты и инструкции хранятся
вместе. Рабочие ключи, личные OAuth-токены, база данных, журналы и загружаемые
пользователями материалы в Git не помещаются.

Название ветки само по себе не доказывает, какая версия установлена на сервере.
Для выпуска нужны точный Git-коммит, контрольная сумма исходного архива и
идентификатор собранного Docker-образа.

## Как проверяется сборка

Подготовлен отдельный способ сборки из официального Python-образа с фиксированной
контрольной суммой. Ему не нужны прежние образы Gateway и цепочка ручных наложений.
Версии Python-библиотек и их допустимые SHA256 закреплены в `gateway/locks`.
Пакеты Debian также закреплены по версиям и дате подписанного архива.

Код устанавливается из одного Python-пакета. Дублирующая исходная копия
в `/app` в новом образе отсутствует. Сборка проверяет состав зависимостей,
миграций, неизменность SDK Битрикс24 и соответствие кода принятой версии.
Проверка не меняет права сотрудников и не обращается к рабочему UniSender.

Фиксация версий не означает, что зависимости можно не обновлять. Обновление
версий — отдельное изменение с повторными тестами. Доступность внешних архивов
также нужна для повторной загрузки зависимостей.

## Где разработчику смотреть автоматическую проверку

После публикации настройки откройте
[репозиторий → Actions](https://github.com/Coffeecan-Oleg/ai-native/actions)
и выберите «Corporate Gateway pinned release». Внутри конкретного запуска
смотрите шаги проверки ресурсов, сборки, тестов и новой временной базы.

Queued означает ожидание, In progress — выполнение, Success — успешное
завершение именно этого сценария, Failure — ошибку. При ошибке выпуск
не считается проверенным; сначала нужно прочитать причину в упавшем шаге.

В блоке Artifacts появится файл с именем gateway-ci и номером запуска.
В обычном CI сохраняются JSON-отчёты: проверка ресурсов, установленного пакета,
регрессии, запуска с новой БД и общий итог. Отчёты хранятся семь дней.
Это не резервная копия и не файл Docker-образа.

Сборка идёт на отдельной машине GitHub. Рабочие ключи Битрикс24/UniSender,
личные токены и данные сотрудников ей не передаются. Временная БД содержит
только состояние теста. Песочница во время этой сборки не используется.

Зелёный результат CI не обновляет Платформу автоматически и не подтверждает
новый личный вход в настоящий Битрикс24 или вызов рабочего UniSender.

## Как читать статусы выпуска

- «Исходники сверены» — код сопоставлен с установленным Gateway.
- «Образ собран» — получен отдельный кандидат из исходников.
- «Тесты на копии пройдены» — проверены указанные сценарии с вымышленными данными.
- «Применён» — администратор после согласования обновил работающий Gateway.
- «Принят» — после обновления отдельно проверены HTTPS, MCP и приложение Битрикс24.

Первые три пункта не заменяют два последних. Проверка синтетического входа
не подтверждает новый личный вход сотрудника в действующий портал.

## Как администратору готовить обновление

1. Зафиксировать точный состав изменения и результат проверки на копии.
2. Показать владельцу эффект, ограничения, порядок проверки и отката.
3. После согласования сделать закрытую резервную копию.
4. Обновить только согласованный сервис, сохранив права, секреты и данные.
5. Проверить HTTP-состояние, реальный вызов MCP и открытие приложения в Битрикс24.
6. Записать итог и обновить соответствующую инструкцию.

Полный порядок эксплуатации:
[Корпоративная MCP Платформа: эксплуатация и порядок обновления](https://akmetron.bitrix24.ru/note/document/495/).

## Доставка образа для согласованного выпуска

Для вечернего выпуска5ноября предусмотрена отдельная ветка
`delivery/platforma-evening-20261105`. Только запуск из этой ветки после
проверок экспортирует принятый образ и delivery.json в артефакт со сроком
хранения один день. Образ содержит исходники и публичные зависимости;
рабочие .env, базы, пользовательские загрузки и подключённый каталог навыков
в него не включаются. Это не автоматическая выкладка и не публичный реестр образов.

Для скачивания артефактов GitHub требует вход и чтение репозитория:
[официальная инструкция](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/download-workflow-artifacts).
У публичного форка такой доступ не равен закрытому корпоративному хранилищу,
поэтому секреты и рабочие данные туда не помещаются.

Перед передачей через разрешённый `load` сверяют SHA256 архива, image ID,
Git-коммит и точный тег `platforma-gateway:evening-<коммит>`. Новая миграция
применяется согласованным способом после снимка. Затем выполняют `deploy`
и отдельную приёмку. Образ ничего не записывает в подключённые каталоги знаний
и встроенных навыков.

## Где смотреть фактический статус

Эта статья описывает порядок работы, а не доказывает последнюю выкладку.
Фактические commit/image ID, миграции, проверки и откат записываются в отчёт
конкретного выпуска. В новом образе `/healthz` читает Git-коммит из файла образа,
поэтому старое значение GATEWAY_RELEASE_SHA в compose не маскирует новую версию.
