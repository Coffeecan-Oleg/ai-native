# Разработка и выпуск Платформы

Пакет объединяет постоянный dev-контур, проверку образа из CI и управляемый выпуск.
Текущий статус установки смотри в отчёте, а не определяй по наличию этих файлов в Git.

## Обычный цикл

1. Разработчик меняет код в отдельной ветке, запускает тесты и показывает пакет владельцу.
2. После согласования публикации CI проверяет исходники и собирает образ.
3. Принятый образ проверяется и устанавливается в dev. Там проверяются функции и отказы.
4. Владелец принимает результат и разрешает конкретный выпуск в production.
5. Тот же образ, без пересборки, проходит управляемое окно. После открытия выполняется личная приёмка.

Общие команды сервера и сеть меняются отдельным согласованным пакетом. Для изменения
обычной функции MCP обращаться к инфраструктурному оператору не требуется.

## Что входит

- development.py, dev_bootstrap.py — создание нового отдельного контура platformadev.
- dev_main.py — команды выпуска только для dev на kromin. Production-БД и проект отвергаются.
- main.py, release_control/ — общий механизм выпуска и отдельный защищённый вход для production.
- workflow.py — клиент Windows/Linux: проверка артефакта CI и выбор явного окружения.
- configure_dev_bitrix.py — разовая настройка собственного приложения Bitrix24 через скрытый ввод.
- dispatcher-integration.py — фрагмент интеграции в существующий ограниченный SSH, не его замена.
- tests/ — unit-тесты и отдельная репетиция на вымышленных данных.

Пакет использует стандартную библиотеку Python 3.12+ и уже имеющиеся Docker Compose v2,
systemd, PostgreSQL tools внутри контейнера и Caddy. SSH-ключ остаётся на компьютере владельца.

## Первый запуск dev — после согласования установки

Из проверенного распакованного пакета на kromin, под sudo:

    python3 dev_bootstrap.py plan

Сохранить JSON в закрытый файл, проверить изменения и SHA256. Затем:

    python3 dev_bootstrap.py apply /path/to/reviewed-plan.json PLAN_SHA256

Результат: /opt/platforma-dev, проект platformadev, БД gateway_mcp_dev,
четыре отдельных тома, worker platforma-dev-release-worker.service и порт 127.0.0.1:18081.
Ключи БД, JWT и шифрования токенов генерируются на сервере. Суммарный лимит контейнеров — 640 МиБ.
Данные и секреты старой песочницы/production не копируются. При конфликте проекта, порта,
каталога, unit, образа или плана установка отказывается продолжать.

Сначала это технический dev: /healthz работает, /mcp без токена возвращает 401,
а личный вход сообщает, что отдельное приложение ещё не настроено. Проверить через SSH-туннель:

    ssh -N -F SSH_CONFIG -L 127.0.0.1:18081:127.0.0.1:18081 aiport

Открыть http://127.0.0.1:18081/healthz. Полноценный вход сотрудников потребует публичного
HTTPS-маршрута и отдельного приложения Bitrix24; см. operator-handoff.md.

## Образ из CI

После согласованной публикации ветки delivery/platforma-* CI сам выполняет проверки и
экспортирует принятый образ. Это не выкладка на сервер. Артефакт хранится семь дней.
Также предусмотрен workflow_dispatch с export_image=true; доступность ручного запуска
зависит от наличия workflow в default-ветке GitHub. Ветка доставки работает без этой зависимости.

    python workflow.py verify-delivery --archive image.tar.gz --report delivery.json

Проверяются SHA256 всего архива, размер, единственный тег, commit, config digest и UID.
Config digest и OCI manifest digest — разные значения. Валидатор ничего не загружает и не запускает.
После установки нового пакета инструментов для загрузки проверенного образа в dev:

    python workflow.py import-image --environment dev --archive image.tar.gz --report delivery.json --ssh-config SSH_CONFIG

Команда проверяет архив и место на ПК и сервере, сериализует импорт с выпуском,
не меняет контейнеры и не выполняет deploy. PowerShell не обрабатывает двоичный
поток: передачу выполняет Python. Конфликт тега, ошибка квоты и повреждение архива
блокируют load. Неизвестный результат блокирует повтор до разбора; не повторять
ручной docker load. [Описание и ограничения](../../gateway/docs/knowledge-base/19-guarded-dev-import.md).

Перед импортом после установки нового пакета инструментов:

    python workflow.py storage-check --archive image.tar.gz --report delivery.json --ssh-config SSH_CONFIG

Это проверка только чтением: локальная валидация артефакта и фиксированная команда
на dev. Учитываются распаковка, копии слоёв, остаток Btrfs-квоты и резерв. Команда
ничего не загружает, не запускает и не удаляет. Ненулевой код блокирует продолжение
процесса; ручной docker load сам по себе эту проверку не вызывает. Контроллер также
заново проверяет место до окна. Статус установки и пределы поддержки:
[проверка квоты](../../gateway/docs/knowledge-base/18-storage-preflight.md).

## Выпуск в dev

    python workflow.py release --environment dev --ssh-config SSH_CONFIG plan IMAGE_TAG
    python workflow.py release --environment dev --ssh-config SSH_CONFIG apply PLAN_ID PLAN_SHA256
    python workflow.py release --environment dev --ssh-config SSH_CONFIG current
    python workflow.py release --environment dev --ssh-config SSH_CONFIG report OP_ID
    python workflow.py release --environment dev --ssh-config SSH_CONFIG accept OP_ID

Apply создаёт systemd-задачу и не зависит от открытого терминала. План фиксирует исходную
версию, настройки и image ID. Вход закрывается до остановки Gateway и финального снимка.
Миграция выполняется отдельно. Awaiting_accept означает техническую готовность при закрытом входе.
Accept — отдельный допуск. Основная БД PostgreSQL копируется через pg_dump; три прикладных
тома копируются отдельно. Том postgres не заменяется сырым копированием работающего кластера.

## Отказ

До допуска записей: recover OP_ID, проверка прежней версии, затем reopen-previous OP_ID.
Неподтверждённое закрытие входа и попытка открытия запрещают возврат старого снимка.
Если SQL продолжился после остановки контейнера, restore блокируется. Известный запрос
нужно дождаться; неизвестный или зависший запрос требует диагностики оператора.
Контроллер не завершает чужие подключения PostgreSQL.

После открытия используется совместимое исправление вперёд. Полный возврат старой БД
может потерять новые записи и требует отдельного решения владельца. Image-only rollback
старого SSH-интерфейса не заменяет этот процесс.

## Разовый вход Bitrix24

После настройки публичного HTTPS создать ОТДЕЛЬНОЕ локальное приложение на akmetron.bitrix24.ru:
обработчик https://platforma-dev.akmetron.ru/auth/bitrix24/callback,
установка https://platforma-dev.akmetron.ru/auth/bitrix24/install, право user_brief.
Рабочее приложение не изменять. Принятие условий выполняет владелец.

Из пакета на сервере через ssh -tt запустить configure_dev_bitrix.py stage и ввести
новые Client ID/Secret скрыто, не передавая в чат. Member ID можно оставить пустым:
реализация привязывает портал и проверяет фактический личный вход.
Stage только сохраняет защищённую pending-конфигурацию. Затем plan проверяет реальный
HTTPS и выдаёт изменения без значений секретов; apply применяется после просмотра.
Последним шагом владелец входит лично. Наличие настроек не считается успешным OAuth.

## Получение ответа инфраструктуры без пересылки сообщений

Новый клиент умеет читать несекретную квитанцию через единственную команду
`files get runtime/workflow-handoff.json`. Никаких load/apply/deploy и сетевых
переходов по значениям квитанции нет. Проверка не выдаёт разрешения на выпуск.

    python workflow.py handoff --ssh-config SSH_CONFIG --expected-package-sha256 REVIEWED_PACKAGE_SHA256

Для проверки сохранённого файла вместо `--ssh-config` используется `--receipt FILE`.
Пример схемы — handoff.example.json. Оператор добавляет `recorded_at` в формате UTC
`YYYY-MM-DDTHH:MM:SSZ` по фактическому времени проверки. Без даты либо старше24 часов
квитанция считается неактуальной для готовности; сам файл остаётся читаемым.

Клиент проверяет пакет, точный dev URL, строгие булевы флаги и два разрешённых пути
read-only исходников с хешами. Новые поля, секретные поля и произвольные пути
отклоняются. Поле notes никогда не печатается. Размер ответа ограничен16 КиБ;
ожидание SSH ограничено. Пропавшая квитанция означает `handoff_receipt_unavailable`,
а не неисправность Gateway. Все флаги помечаются как сообщение оператора,
не независимая проверка. Даже полный ответ требует личной приёмки и согласования.

Пример не устанавливается на сервер автоматически. Размещение квитанции и исходников
выполняет оператор после согласования. Не применять files apply только ради этого
информационного файла: текущая реализация пересоздаёт Gateway для runtime apply.

## Ограничения установки

В dev нет реального UniSender, рабочих списков, памяти владельца и статистики production.
Снимки локальные, автоматическая ротация и внешнее резервирование здесь не настроены.
Bootstrap не переустанавливает существующий dev и не удаляет его данные.
Уже выданный полный sudo в dev сохраняется; production получает только согласованные команды.
Изменения .env, секретов и общих host-настроек не подменяются произвольным image-only релизом.

Источник семантики CI: https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax


## Одноразовая диагностика и репетиция восстановления

`operations_check.py` выполняет только три команды чтения SSH и четыре публичных
HTTP-проверки с ограничением времени и размера ответа. Требует проверенный конфиг
с alias `platforma-production` и полный SHA ожидаемого выпуска. Ничего не
перезапускает и не отправляет уведомления. Запуск из корня репозитория:

    python tools/platforma-workflow/operations_check.py --ssh-config SSH_CONFIG --expected-revision f95be3a63c65417ef821f278dba7095d7098cf68 --output operations-report.json

Код 0: все технические проверки прошли. Код 1: есть отказ или неизвестный результат.
В отчёте нет сырого вывода SSH, заголовков, cookie и секретной конфигурации.
Версия схемы 28 и формат тега закреплены в текущем контракте; после их изменения
проверку нужно обновить вместе с тестами. Отчёт не подтверждает приёмку сотрудником,
внешнюю копию, свободную квоту, доставку уведомлений или контроллер production.

`tests/rehearse_restore_current.py` — отдельная разрешаемая репетиция на dev-хосте
kromin: новый временный PostgreSQL, вымышленные данные, текущий закреплённый образ,
дамп/восстановление, сравнение всех таблиц и файлов, запуск восстановленного Gateway.
Она не входит в обычные unit-тесты и не читает рабочие данные. Нужны root, Docker,
локально загруженные принятые образы, запас RAM и Btrfs-квоты. Хостовые порты не
публикуются. Временные ресурсы помечены уникальной меткой и удаляются в finally;
восстановление реальной production-копии этим не считается проверенным.

Полный разбор: `gateway/docs/knowledge-base/20-operations-and-recovery.md`.
